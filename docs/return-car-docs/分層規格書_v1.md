# iRent 智能車況管家 — 分層規格書 v2

還車照片處理流程的四層規格。每層獨立定義職責、輸入輸出、調校目標與失敗行為。

## v2 主要變更

| # | 變更 | 影響層 |
|---|---|---|
| 1 | **改為阻塞式**：使用者需等待 L1 回覆，取代原「樂觀放行」 | L0 / L1 |
| 2 | **可判讀性由 L1 判定**，不是端上純運算能決定的事 | L0 / L1 |
| 3 | **L1 改為單張車損偵測**，不做新舊判定；文字車損紀錄降為未驗證提案 | L1 / L2 |
| 4 | **L2 降為確認層**，只在疑似新車損時才調照片做影像對照 | L2 |
| 5 | **L3 重構**：除「可租用」外，所有狀態的後續行動一律需人工 | L3 |
| 6 | **狀態收斂為三種**：「待查驗」與「停用派修」合併為「停用」，路由改由 `reason` 決定 | L3 |
| 7 | 成本數字更新（L1 於取車、還車都要跑） | 全域 |

---

## 貫穿全文的設計原則

1. **每層只回答一個問題。** 層與層之間用結構化資料溝通，不共用判斷邏輯。
2. **調校目標逐層反轉。** L0 寧可放行、L1 寧可錯殺、L2 寧可保留、L3 寧可保守。
3. **失敗時往保守側倒。** 讓髒車或損車進入下一單的代價，遠大於多一次人工複核。
4. **狀態改變可自動，資源投入一律經人。**
   AI 可以讓車輛「不可租」——這是保護性的、可逆的、保護下一位用戶的動作。
   但 AI 不可以派人、不可以花錢、不可以扣款。**這是 v2 最重要的一條。**
5. **AI 只能把車移出「可租用」，不能把車移回「可租用」。** 唯一例外是還車檢查全數通過的自動放行。一旦被標記，只有人能解除。

| | L0 拍攝防呆 | L1 快篩 | L2 影像確認 | L3 決策派工 |

| **位置** | 手機端 | 伺服器 | 伺服器 | 伺服器 |

| **技術** | 現成模型＋純運算 | VLM | VLM | 規則引擎（非 AI） |

| 階段 | 呼叫數 | 成本 |
|---|---|---|
| 取車：車外 4 張 | 4 | $0.037 |
| 還車：車外 4 張＋車內 2 張 | 6 | $0.056 |
| L2 確認（僅疑似新車損，約 10–15%） | ~0.5 | ~$0.015 |
| **合計** | | **≈ $0.11/趟** |

## L0 — 端上拍攝防呆

### 職責

在拍攝當下擋掉**粗糙的失敗**，讓照片根本不會產生。

**L0 不判定「這張能不能判車損」。** 那是語意判斷，只有 L1 做得到（見下）。L0 的價值在於**讓 L1 的退件變成罕見事件**——若沒有 L0，糊掉、太遠、沒拍到車的照片會一路上傳、讓使用者等 7 秒、再被退件，這是最痛的體驗。有 L0 先擋，L1 退件率可望降到 2–5%，阻塞式等待才可以忍受。

### 輸入

相機即時影像串流，10–15 fps。

### 檢查項目

| 項目 | 方法 | 門檻（起始值，需校準） |
|---|---|---|
| 車體存在 | 物件偵測 bbox | conf > 0.7 |
| 畫面佔比 | bbox 面積 / 畫面 | 0.35 – 0.85 |
| 完整性 | bbox 是否貼齊畫面邊緣 | 四邊留白 > 2% |
| 清晰度 | Laplacian variance | > 100（需依機型校準） |
| 曝光 | 直方圖過曝／過暗像素比 | 各 < 15% |
| 連續確認 | 上述全通過的連續幀數 | ≥ 5 幀（約 0.3s） |
| 角度正確 *(後續)* | 角度分類器 | 目標角度 conf > 0.8 |
| 匡線對齊 *(後續)* | 車型專屬輪廓 IoU 或關鍵點排列 | IoU > 0.65 |
| 穩定度 *(後續)* | 陀螺儀角速度 | < 0.15 rad/s |
| 車牌 *(後續)* | OCR 比對訂單車牌 | 文字相符 |

### 輸出

觸發快門，照片附帶品質 metadata：

```json
{
  "photo_id": "p_8f3a...",
  "order_id": "47352776",
  "car_no": "RDS-6583",
  "stage": "return",
  "slot": "左前",
  "capture_mode": "auto",
  "l0": {
    "passed": true,
    "car_coverage": 0.62,
    "blur_score": 128.4,
    "exposure": { "over": 0.02, "under": 0.05 },
    "frames_confirmed": 5
  }
}
```

### 調校目標：高通過率

**這一層唯一調錯方向會出大事的地方。** 用戶站在停車場，快門就是不觸發 → 放棄還車 → 商業損失遠大於一張品質普通的照片。

漸進放寬策略：

```
0–15s    嚴格門檻
15–30s   放寬 20%，並顯示卡在哪（「請再退後一步」）
30s+     開放手動快門，標記 capture_mode="manual"
```

### 失敗行為

手動快門的照片標記 `l0_bypassed: true`，L1 對這些照片加強可判讀性檢查。

### Hackathon 實作範圍

**平台：瀏覽器（Web），非 native app。** 用 `getUserMedia` 抓相機串流＋Canvas 處理。評審用手機瀏覽器就能操作，不需簽署部署 native app，開發風險最低。

**核心先做 5 項，不需要任何訓練資料：**

| 項目 | 方法 |
|---|---|
| 車體存在＋畫面佔比 | TF.js `coco-ssd`（COCO 內建 car 類別，現成模型直接載入） |
| 完整性（四邊留白） | 同一個 bbox，檢查是否貼齊 canvas 邊界 |
| 清晰度 | Canvas 像素資料算 Laplacian variance |
| 曝光 | Canvas 像素直方圖，過曝／過暗像素比 |
| 連續確認 | 上述檢查連續 N 幀通過才觸發快門 |

**暫緩項目**：角度分類、匡線對齊、車牌 OCR、陀螺儀穩定度。這四項要嘛需要訓練資料、要嘛需要車型比對表，非 hackathon 時間內能做完整，列入後續規劃。

角度防呆若想保留視覺效果，可用取巧做法：畫面疊一個固定的半透明引導框（非模型分類），使用者對齊後用 bbox IoU 判斷是否對準——本質是幾何檢查不是 AI，成本接近零，但能維持「角度防呆」的產品敘事。

### 技術選型

**Hackathon 版本：TF.js + MediaPipe（瀏覽器）。** 正式產品若下放到 native app，可延用同一組檢查邏輯，換成 MobileNetV3-Small 或 YOLOv8n 級別的模型，跑 TFLite / ONNX Runtime Mobile。

### 訓練資料

**Hackathon 階段可跳過此節**——核心 5 項用現成模型與純運算完成，不需訓練資料。以下保留給角度分類器等暫緩項目。

- **正樣本**：xlsx 下載的 26,000 張（`ImageType` 1/2/3/4 為車外）
- **負樣本**：程式化退化生成 — motion blur、gamma 壓暗＋低光雜訊、局部過曝、裁切、旋轉、透視變形、遮蔽車牌、JPEG q10–30
- **注意**：合成退化 ≠ 真實退化。訓練用合成，**評估必須用真實爛照**

### 評估指標

- 自動觸發成功率（多少比例的還車不需要手動 fallback）
- 平均觸發耗時
- 放棄率
- **L1 退件率**（L0 有效性的真正指標：L0 做得好，L1 就很少需要退件）

## L1 — 伺服器端快篩（阻塞）

### 職責

單次 VLM 呼叫，回答三件事：

1. **可判讀性**（最優先）— 這張照片能不能用來判斷車損？
2. **單張車損偵測** — 這張照片上看得到損傷嗎？屬於哪一類、多嚴重？
3. **車內整潔度**（僅車內照）— 髒汙／普通／乾淨

L1 **不判斷損傷是新是舊**。單張照片沒有基準線，判不出來，那是 L2 的事。

### 可判讀性與覆蓋範圍是兩件事

這兩者常被混為一談，但下游處理完全不同，必須分開：

| | 問什麼 | 受什麼影響 | 車損結果 | 重拍提示 |
|---|---|---|---|---|
| **可判讀性** | 畫面裡的車身表面看不看得出漆面狀況 | 模糊、過暗、反光、遮擋 | **必須丟棄** | 「請避開光源」「請保持穩定」 |
| **覆蓋範圍** | 該角度的主要部位有沒有都入鏡 | 距離過近、裁切 | **仍然有效** | 「請退後一步」 |

**一張只拍到左前保險桿的特寫，若那塊保險桿清清楚楚，就是「可判讀 ＋ 覆蓋不足」。**
它看到的裂痕應該被記錄下來，只是另外要求補一張更廣的。

這個區分不是學術潔癖——索賠案件的損傷照大多是特寫。若把「距離過近」歸入不可判讀，
等於把最重要的損傷樣本全部作廢。

### 為什麼可判讀性必須由 L1 判定

**「照片品質」與「這張能不能判車損」不是同一件事。**

一張照片可以完全清晰、曝光正常，但仍然無法判讀：

- 車只佔畫面 10%——很銳利，但看不出刮痕
- 車身濕的或積了灰，漆面狀況被遮住
- 那一面正好整片反光或落在深陰影裡
- 拍到的是對的角度但錯的那一面

這些純訊號處理全都抓不到。**只有理解「我看不看得出這個面有沒有傷」的模型才判得出來**，所以這一項必須在 L1，也是使用者需要等待 L1 的唯一理由。

### L1 輸出什麼

以車輛部位為索引的損傷清單，含類型與嚴重度。**不做新舊判定。**

損傷分類採 SOCAR 實際營運驗證過的三類，另加兩類：

| 類型 | 說明 |
|---|---|
| 刮痕 | 表面刮擦，可能未見底漆 |
| 凹陷 | 鈑件變形凹陷 |
| 板件間隙 | 鈑件被撞開、翹起、產生縫隙（碰撞指標） |
| 破裂 | 保險桿、燈殼破損 |
| 缺件 | 零件缺失 |

嚴重度分四級，分界對齊 L3 的營運動作（`severity ≥ 3` 才拉車）：

| 等級 | 定義 |
|---|---|
| 無 | 車身完好，或只有洗得掉的髒污水漬 |
| 輕微 | 刮痕擦傷，漆面有痕跡但鈑件未變形 |
| 中度 | 凹陷、明顯破損、鈑件變形 |
| 嚴重 | 結構性損壞、零件脫落、必須進廠 |

### 觸發時機：取車與還車都要跑

**還車**：完整三項（可判讀性、單張車損偵測、車內整潔度）。

**取車**：只跑車外（可判讀性、單張車損偵測）。結果存入車輛歷史，作為還車時 L2 配對比對的基準線。

取車照同時有第二個用途：如果**取車時就偵測到損傷**，代表損傷發生在閒置期間（維修移車、鄰車擦碰、停車場擦撞），**不該算在任何一位用戶頭上**，應路由到「維修／營運異常」佇列而非客訴求償路徑。這一步是在保護使用者。

車內整潔度只在還車跑；取車時的車內狀態不影響清潔派工判斷。

### 輸入

單張照片 + 訂單 metadata（`order_id`、`car_no`、`stage`、`slot`）+ L0 品質分數。

**不需要餵入任何歷史資料** —— L1 只看這一張。

### 輸出

車外照：

```json
{
  "photo_id": "p_8f3a...",
  "assessable": true,
  "assessable_reason": null,
  "retake_required": false,
  "angle_verified": "左前",
  "angle_conf": 0.91,
  "angle_mismatch": false,
  "observed_damages": [
    { "part": "左前葉子板", "type": "刮痕", "severity": "minor" },
    { "part": "前保險桿左側", "type": "破裂", "severity": "moderate" }
  ],
  "max_severity": "moderate",
  "escalate_to_l2": true,
  "model": "gemini-3.6-flash",
  "latency_ms": 6700,
  "cost_usd": 0.0093
}
```

不可判讀時：

```json
{
  "photo_id": "p_9d02...",
  "assessable": false,
  "assessable_reason": "車身左側整片反光，漆面狀況無法判讀",
  "retake_required": true,
  "retake_hint": "請換一個角度避開光源，或退後一步",
  "observed_damages": null,
  "escalate_to_l2": false
}
```

車內照：

```json
{
  "photo_id": "p_9c21...",
  "assessable": true,
  "cleanliness": "髒汙",
  "cleanliness_conf": 0.88,
  "items": ["飲料杯", "食物包裝"],
  "escalate_to_l2": false
}
```

### 一次呼叫，不要拆成兩次

VLM 的成本主要在**輸入的影像 token**，不在輸出。「先只檢查可判讀性、不合格才不做車損分析」這個省法，省下的只有輸出那一小段——影像 token 照付。拆成兩次呼叫反而多一個來回，對阻塞式設計是反效果。

**做法：一次呼叫同時回傳可判讀性與車損結果，用邏輯做 early return**（不可判讀就丟棄車損結果、不寫入紀錄、直接要求重拍）。

early return 在這裡的價值是**省使用者的時間，不是省錢**——而且若在同一次呼叫內，連時間也省不到。認清這點可以避免為了假的成本優化增加架構複雜度。

### 使用者體驗：逐張回報，不要單一 spinner

benchmark 實測 Gemini Flash：平均 6.7s、p95 11.7s、最大 13.1s（單張）。6 張並行、等最慢那張：

`1 - 0.95⁶ = 26%` 的使用者會等超過 11.7 秒。

**解法不是減少等待內容，是逐張回報。**

```
左前 ✓   右前 ✓   左後 ⏳   右後 ✗ 反光過強，請換角度
前座 ✓   後座 ⏳
```

- 使用者看得到進度，心理等待時間大幅縮短
- **被退件的那張可以立刻重拍，不必等其他張跑完**——把序列化等待變成重疊
- 感受上的延遲從「最慢那張」變成「第一張回來的時間」

### 重拍迴圈必須有上限與出口

重拍後又被退件怎麼辦？

**上限 2–3 次，超過即接受照片、標記 `quality_forced: true`、路由至 **停用**（`reason: unassessable`）。**

沒有這個出口，會出現「使用者怎麼拍都過不了、被困在還車流程裡」——這是整個系統最糟的失敗，比漏判車損嚴重得多，因為它直接卡住營收且百分之百變成客訴。

### 車損結果不告知使用者

使用者只會收到兩件事：**照片是否合格**、**車內是否整潔**。車損判定結果不在當下揭露。

理由：AI 判定尚未經人複核，**在無人的停車場當場指控使用者刮傷車輛，是最糟的信任災難**。應由客服備妥證據後再聯繫。

但要意識到：由於使用者等的是同一次 L1 呼叫，**車損結果在他還站在現場時就已經存在**，只是選擇不告知。這是刻意的產品決策而非技術限制，因此配套必須做到：

- 還車確認畫面明載「車況檢查已完成，如有異常我們會於 X 小時內主動聯繫」
- 嚴重車損設 SLA（建議 2 小時內），不是隔天
- 通知一律附證據圖與申訴入口

**摧毀信任的不是「事後才發現」，是「延遲且無憑無據的事後發現」。**

### 調校目標：高 recall

**L1 漏掉的永遠不會再被看到**（後面沒人回頭檢查），但 L1 誤報只是多花一次 L2 呼叫。兩種錯誤代價不對等。

benchmark 實測（50 張樣本）：

| 門檻 | Gemini 3.6 Flash | 適用層 |
|---|---|---|
| `any` | recall **100%**（23 台有損零漏判），9 誤報 | **L1** |
| `moderate` | precision 100%，recall 降至 91.3% | L2 / L3 |

benchmark 推薦 `moderate` 是因為它評估的是**單層系統**——同一個門檻要兼顧過濾與裁決。多層架構應把嚴重度門檻後移到 L2/L3，L1 吃滿 recall。

### 可判讀性的 prompt 要獨立設計

benchmark §8 實測：`retake_required` 在 200 次呼叫中觸發 **0 次**，包括一張暗到、糊到無法判讀的照片，四個模型全都回「無車損」。

**這代表把可判讀性當成車損 prompt 的附帶問題問，是行不通的。** VLM 有強烈的「有問必答」傾向。

對策：

- 在 prompt 中**先問可判讀性、再問車損**，並明確要求「若無法判讀，`observed_damages` 必須為 null」
- 給出具體的不可判讀情境清單（反光、陰影、過遠、遮蔽、濕污）
- 建立**刻意的爛照片測試集**專門校準這一項（benchmark §9 亦列為待辦）

### 失敗行為（fail-open 到下一層）

| 狀況 | 行為 |
|---|---|
| VLM 逾時 / 錯誤（重試 3 次後） | 對使用者顯示「檢查中，稍後通知」並放行；車輛轉 **停用**（`reason: system_error`）|
| JSON 格式錯誤 | 重試；仍失敗比照逾時 |
| 角度信心 < 0.6 | 標記 `angle_uncertain`，不阻擋 |
| `assessable: false` 且未達重拍上限 | 要求重拍該張 |
| `assessable: false` 且已達重拍上限 | 接受、標記 `quality_forced` → 停用（`unassessable`）|

原則：L1 掛掉不能導致有損傷的車被放行，但也不能把使用者困在現場。

### 評估

全部使用**人工逐張標註**的 ground truth，不使用資料夾名稱推導的標籤。

| 指標 | 資料集 | n |
|---|---|---|
| **單張車損偵測** precision / recall | `labeling/damage/` 人工標註 | 293 |
| **嚴重度分級**準確率（4 級） | 同上 | 293 |
| **可判讀性**準確率 | `labeling/label_assessability.html` 人工標註 | 400 |
| **車內整潔度**（含誤傳偵測） | `labeling/curated/` 人工標註 | 150 |
| 升級率 | 上述任一 | — |
| 退件率 | 可判讀性集 | 400 |

**為什麼不用資料夾名稱當標籤。** `進行索賠資料` 的 32 張損傷照中，
經逐張檢視發現 **7 張（約 22%）從該角度根本看不到損傷**——理賠確實成立，
但照片拍的是完好的那一面。若直接用資料夾當標籤，模型正確回答「無損傷」反而被算錯。

benchmark 報告 §5 記錄過同樣現象：修正 50 張中的 4 個標籤後，
領先模型的準確率從 84% 跳到 92%。**標籤品質的影響大於模型選擇。**

**必報的對照基準。** 車損為稀有事件，若測試集中僅少數有損傷，
「永遠回答無損傷」就能得到很高的準確率。因此：

- 必須報出 trivial baseline（永遠回答無損傷的準確率）
- 必須分類別報 precision / recall 與各自樣本數，不得只報整體準確率
- 每個數字附 95% 信賴區間

**干擾物子群分析。** 標註時另有「有干擾物（水漬／反光／陰影／髒污）」標記。
可據此拆出「有干擾物 vs 無干擾物」兩組分別計算誤報率——
兩者的差距直接量化了 prompt 對干擾物的抵抗力，是調校最有用的單一訊號。

## L2 — 影像確認層

### 職責

只在 L1 偵測到車損時觸發，回答：**「這個損傷是這趟造成的嗎？」**

L1 是便宜的粗篩（單張、高 recall），L2 是昂貴的確認（配對、高 precision）。只有真的可能要跟使用者收錢時才付這個成本。

L2 不再是預設路徑。**紀錄比對是便宜的粗篩，影像對照是昂貴的確認**，只有真的要跟使用者收錢時才付這個成本。

### 處理方式

調出該車**這趟的取車照**（同部位角度），與還車照做影像對照。

**不要把兩張圖丟給 VLM 叫它「比較」。** 光線、角度、背景、地面全都不同，模型會被無關差異干擾而腦補。

```
Stage A（VLM）  分別描述兩張照片的損傷，以「車輛部位」為索引
Stage B（程式） 集合差： damages(還) - damages(取)
```

**用車輛部位當座標系，不要用像素座標。** 兩張照片無法精確對齊，但「左前葉子板」在兩張裡是同一個東西。這繞過了 VLM 定位不精準的弱點，也省掉影像配準。

### 損傷分類

採 SOCAR 實際營運驗證過的分類，另加兩類：

| 類型 | 說明 |
|---|---|
| 刮痕 | 表面刮擦，可能未見底漆 |
| 凹陷 | 鈑件變形凹陷 |
| 板件間隙 | 鈑件被撞開、翹起、產生縫隙（碰撞指標） |
| 破裂 | 保險桿、燈殼破損 |
| 缺件 | 零件缺失 |

### 輸出：必須是三態

```json
{
  "photo_id": "p_8f3a...",
  "car_no": "RDS-6583",
  "baseline_photo_id": "p_pickup_3c1...",
  "baseline_available": true,
  "findings": [
    {
      "part": "前保險桿左側",
      "type": "破裂",
      "verdict": "新增",
      "severity": 3,
      "confidence": 0.83,
      "reason": "保險桿左下方見約 8cm 裂痕與漆面剝落。取車照同部位清晰可見且完整無損。",
      "evidence_crop": "crop_8f3a_01.jpg"
    }
  ],
  "max_new_severity": 3,
  "unclear_parts": []
}
```

`verdict` 三態定義：

| 值 | 條件 |
|---|---|
| `新增` | 還車照有、取車照沒有，**且該部位在取車照中清晰可見** |
| `既有` | 取車照就有 |
| `無法判定` | 還車照有，但該部位在取車照被遮擋／模糊／未入鏡 |

**第三態是這一層最重要的設計。** 沒有它，取車照沒拍好的案例會被誤報成新傷，系統會誤扣押金。有了它，這些案例會誠實地進人工佇列。

### 幻覺抑制

- `temperature = 0`
- 強制 JSON schema
- 中性問法（不要問「損傷在哪裡」，要問「是否有損傷，若無請回報 false」）
- prompt 明確排除：水漬、灰塵、反光、陰影、雨滴、地面倒影不算損傷
- `severity ≥ 3` 的案例跑 3 次取多數（self-consistency）

### 調校目標：高 precision

誤判有車損 → 誤扣押金 → 客訴，代價遠高於漏判。門檻對齊 benchmark 的 `moderate`。

### 信心分數可否用於路由

benchmark §8 實測校準度：

| 模型 | 答對時信心 | 答錯時信心 | 可否當路由訊號 |
|---|---|---|---|
| Claude Opus 5 | 0.89 | **0.64** | 可（分離 25 點） |
| Gemini 3.6 Flash | 0.97 | **0.92** | 不可 |

**若要做信心分流，L2 必須用 Opus。** 若用 Gemini，改用 severity 分流。

### 失敗行為

| 狀況 | 行為 |
|---|---|
| 取車照缺失或不可判讀 | `無法判定` → 停用（`undetermined`）|
| VLM 逾時（重試 3 次後） | `無法判定` → 停用（`undetermined`）|
| `verdict: 既有`（取車照就有） | 記入車況履歷，不向使用者求償 |
| Stage B 集合差為空 | 正常結案 → 可租用 |

### 評估

L2 有兩組性質不同的評估資料，**兩組都要報**。

**第一組：120 組人工標註配對（主力）**

`沒有進行索賠` 資料夾的 30 台車 × 4 角度，借還齊全率 100%。
標註後借、還兩側**各自都有損傷清單**，因此可直接檢驗三態判定：

| 情境 | 正確答案 |
|---|---|
| 借無、還有 | `新增` |
| 借有、還也有 | `既有` |
| 借不可判讀、還有 | `無法判定` |

**這是唯一能直接量「新增 vs 既有」判別能力的資料。**
其價值在於能區分「模型真的判對」與「兩側都沒看到而蒙對」——
只有單側標籤的資料做不到這件事。

**第二組：129 組時間結構配對（輔助）**

`pairs.csv` 中 `high_confidence_clean`（同車相鄰訂單間隔 < 1 小時，
車幾乎沒被開走）。正確答案「無新增車損」來自時間結構，不依賴任何人工判斷。

用途是**量誤報率**：系統在這些配對上報出新車損 → 幾乎確定是誤報。
誤報率是本系統最關鍵的指標——誤判有車損 → 誤扣押金 → 客訴，
代價遠高於漏判。

**其他指標**

- **無法判定比例**：太高代表取車照品質不足，需回頭加強 L0
- **`既有` 判定比例**：反映車隊既有損傷的普遍程度，也是判別能力的檢驗

**recall 的限制必須揭露。** 正樣本僅來自索賠資料夾（21 組可配對），
且還車照多為損傷特寫，與真實還車的標準四角度分布不同，n 過小（CI 半寬約 ±13pp）。
**precision／誤報率量得乾淨，recall 只能給有揭露的估計值。**
- **`既有` 判定比例**：反映車隊既有損傷的普遍程度，也是「新增 vs 既有」判別能力的檢驗

## L3 — 決策與派工

### 職責

把 AI 輸出轉換成**車輛狀態改變**與**人的工作佇列**。

### 這一層必須是確定性規則，不是 AI

三個理由：可稽核（客訴時要能說明為什麼這樣判）、可調整（營運隨時改門檻不需重訓）、法遵（涉及金錢的決策鏈必須可解釋）。

### 核心原則：狀態自動，行動經人

L3 分成兩個性質完全不同的子層：

| | 決定什麼 | 誰執行 | 為什麼 |
|---|---|---|---|
| **① 狀態機** | 車能不能租 | **自動** | 保護性、可逆、保護下一位用戶 |
| **② 行動佇列** | 要派誰、要不要收錢 | **一律經人** | 投入資源與金錢，需人負責 |

**除「可租用」外，所有狀態的後續行動都需要人工介入。** 車輛被判定為髒，系統只會把它設為不可租；**要不要派清潔人員，必須由人看過照片後決定。**

理由：AI 的整潔度分類可能誤判（深色椅套、陰影、光影），而派工是實際的人力與成本支出。一次目視確認只要幾秒，但可以避免無效派遣。

### 三種狀態就夠了

狀態只回答一個問題：**這台車現在能不能租？**

原先的「待查驗」與「停用派修」對車輛而言是同一件事——不可租、等人處理。兩者的差異只在「誰來處理」，而那屬於行動層，不屬於狀態。**一旦狀態與行動分離，狀態就不需要再編碼路由資訊。** 因此合併為「停用」，由 `reason` 欄位驅動路由。

| 狀態 | 可租？ | 意義 | 何時解除 |
|---|---|---|---|
| **可租用** | ✅ | 檢查全數通過 | — |
| **待清潔** | ❌ | **有已知解法、時間可預期**（約 30 分鐘） | 清潔完成 |
| **停用** | ❌ | **開放性問題，處理時間未知**（可能是 5 分鐘目視，也可能是 3 天鈑噴） | 人工結案 |

保留「待清潔」獨立的理由不是它比較急，而是**它可排程**。車隊調度可以把待清潔的車算成「30 分鐘後可用」，停用的車則是「未知」。這對可用率預測是完全不同的兩件事。

### 狀態機規則表（依序評估，先命中先套用）

| # | 條件 | 狀態 | `reason` | 進入哪個佇列 |
|---|---|---|---|---|
| 1 | `cleanliness == 髒汙` | 待清潔 | — | 清潔確認 |
| 2 | 取車照即偵測到損傷（閒置期異常） | 停用 | `idle_anomaly` | **維修／營運**（非用戶責任） |
| 3 | `新增` 且 `severity ≥ 3` | 停用 | `new_damage` | 維修確認 **＋** 客服複核 |
| 4 | `新增` 且 `severity < 3` | 可租用 | — | 僅記入車況履歷，不通知使用者 |
| 5 | `無法判定` | 停用 | `undetermined` | 客服複核 |
| 6 | `assessable == false`（含 `quality_forced`） | 停用 | `unassessable` | 客服複核 |
| 7 | L1/L2 逾時或錯誤 | 停用 | `system_error` | 客服複核 |
| 8 | 以上皆非 | 可租用 | — | 無 |

**規則 1 排最前面是刻意的。** 髒汙會在 30 分鐘後直接砸到下一位用戶臉上；車損金額大但理賠可以慢慢談。派工優先序是 **髒汙 > 車損**，與直覺相反。

**規則 2 必須排在車損判定之前。** 「停用」底下有兩種性質完全不同的案件：要跟使用者談的（規則 3、5、6、7），以及跟使用者完全無關、車輛在閒置期間出狀況的（規則 2）。這正是需要 `reason` 欄位的原因——若不區分，客服會把營運問題當成用戶糾紛處理。

**規則 3 同時進兩個佇列，這是刻意的解耦。** 車輛動作與金錢動作是正交的：

| | 目的 | 誰決定 | 時效 |
|---|---|---|---|
| 拉車（移出可租清單） | 保護下一位用戶 | 自動 | 立即 |
| 派維修 | 投入資源 | 維修人員確認 | 小時級 |
| 求償與否 | 釐清責任 | **客服複核** | 小時級 |

信心高低決定要不要動車，**不決定要不要收錢**。求償一律走人工路徑。

**規則 4 是產品決策不是技術參數。** 輕微新損只記錄不求償——對應 benchmark §6 的發現：Gemini 九個誤報全部是 `minor` 等級。把求償門檻拉到 `moderate` 以上，誤報歸零。此門檻應做成營運可調參數。

### 三個人工佇列，由 `reason` 決定去向

| 佇列 | 觸發的 `reason` | 工作內容 | 每件耗時 | 量 | 完成後 |
|---|---|---|---|---|---|
| **清潔確認** | （狀態＝待清潔） | 看車內照片 → 一鍵派工 | 秒級 | 大 | 清潔完成 → 回可租用 |
| **客服複核** | `undetermined`<br>`unassessable`<br>`system_error`<br>`new_damage` | 審證據 → 判定求償／既有／誤報 → **記入車況履歷** | 分鐘級 | 小 | 結案 → 回可租用 |
| **維修／營運** | `idle_anomaly`<br>`new_damage` | 判斷維修範圍 → 排程 | 分鐘級 | 很小 | 完修 → **記入車況履歷** → 回可租用 |

`new_damage` 同時進兩個佇列，這是規則 3 的刻意解耦：維修處理車，客服處理錢。

**只有人能把車移回「可租用」。** AI 唯一能自動放行的情境是還車檢查全數通過（規則 8）。一旦被標記，解除必須經人。

### 客服複核介面必須提供

- 取車／還車照片並排對照
- **該車的車況履歷**（歷次判定與證據圖）
- AI 標註的部位與裁切證據圖
- `reason` 文字說明
- 該車完整車況履歷時間軸
- 一鍵操作：確認求償 / 判定既有損傷 / 標記誤報

**「標記誤報」這個按鈕最重要**——它的回饋是後續模型改進與門檻調校的唯一真實訊號。

**「確認求償」與「記入車況履歷」必須在同一個 transaction 內完成**，否則同一道傷會重複向不同用戶求償。

### 保守側的上限

失敗往保守側倒有個副作用：停用車輛可能堆積，車隊可用率崩掉。

需設監控：停用車輛數超過閾值 → 告警營運。

**`reason` 欄位讓成因分布免費取得**——直接 group by 就知道是 `system_error` 多（系統不穩）、`unassessable` 多（L0 沒擋好）、還是 `new_damage` 多（真的很多人撞車）。這個分布直接指出系統該修哪裡，不需要另外做歸因分析。

## 跨層事項

### 降級策略總表

| 失效層 | 行為 | 理由 |
|---|---|---|
| L0 觸發不了 | 放寬 → 手動快門，標記 `l0_bypassed` | 卡死用戶的代價最大 |
| L1 逾時 | 顯示「檢查中，稍後通知」放行使用者；車輛轉停用（`system_error`）| 不能把人困在現場，也不能放行未檢查的車 |
| L1 判不可判讀且已達重拍上限 | 接受、`quality_forced` → 停用（`unassessable`）| 同上 |
| L2 失效 | `無法判定` → 停用（`undetermined`）| 不能猜 |
| L3 失效 | 車輛預設 `停用`（`system_error`）| 不讓未經判定的車進下一單 |

### 觀測指標

| 層 | 指標 |
|---|---|
| L0 | 自動觸發成功率、平均觸發耗時、手動 fallback 率、放棄率、**L1 退件率** |
| L1 | 可判讀性準確率、退件率、重拍次數分布、升級率、角度不一致率、p95 延遲、成本/趟 |
| L2 | 誤報率、漏報率、無法判定比例、`既有` 判定比例（＝紀錄漏登率）、成本/趟 |
| L3 | 各狀態分布、**停用原因分布（group by `reason`）**、三個佇列長度、客服標記誤報率、清潔派工到完成時間、**車況履歷寫入完成率** |

### 回饋循環

客服在 L3 標記的「誤報 / 漏報 / 既有損傷」是唯一的真實標註來源。累積後用於：

1. 調整 L2 門檻
2. 依 SOCAR 路徑，把 L1 蒸餾成自訓輕量模型（其 Global Damage Classifier 達 96% accuracy/F1），成本再降一個數量級
3. 資料主權考量下，可改用開源 VLM 地端部署

## 附錄：文字車損紀錄 —— 提案，本次未驗證

> **本節描述的是設計提案，不是本次實作的內容，也沒有實驗數據支持。**
> 之所以未驗證，是因為 iRent 現行系統是否有結構化車損紀錄尚未確認，
> 而自行編造一份紀錄再拿去測試自己的系統，得到的數字沒有公信力。

### 構想

每台車維護一份**車損紀錄（damage manifest）**，以車輛部位為索引，
記錄所有已確認的既有損傷。L1 描述影像所見，與紀錄做差集，
紀錄以外的即為疑似新車損。

```json
{
  "car_no": "RDS-6583",
  "updated_at": "2026-04-22T16:47:38+08:00",
  "entries": [
    {
      "entry_id": "dm_0417a",
      "part": "左前葉子板",
      "type": "刮痕",
      "severity": "minor",
      "desc": "約 10cm 水平淺層刮痕，未見底漆",
      "reference_crop": "dm_0417a.jpg",
      "recorded_at": "2026-04-17T09:12:00+08:00",
      "source": "cs_confirmed"
    }
  ]
}
```

### 相對於照片配對的三個優點

1. **不需要配對。** 照片配對依賴取車照拍得好、角度標籤正確、兩張對得上，
   三個依賴任一失效整條就斷。文字清單沒有這些依賴。
2. **角度校正從關鍵降級成加分。** VLM 直接從影像認出「左前葉子板」，
   不需要正確的角度標籤才能比對。
3. **基準線可稽核。** 文字清單是人看得懂、客服可直接調閱的東西。
   爭議時「這道刮痕在您取車前就已登記在案」比「AI 比對了兩張照片」有說服力得多。

### 落地前必須解決的三件事

**① 紀錄更新迴圈是單點故障。**
每次確認新車損後必須寫回紀錄。若沒寫回，下一位用戶還車時同一道刮痕
又會被判成紀錄外的新車損——**同一道傷會重複向不同用戶求償**。
這是所有失敗模式中最嚴重的，一旦發生就是系統性的。
因此「寫回紀錄」必須與「確認求償」在同一個 transaction 內完成。

**② 文字比對有模糊性。**
紀錄寫「左前葉子板 刮痕」，這次也看到「左前葉子板 刮痕」——同一道還是新的？
兩種錯法代價不對等（漏報＝少收一筆錢，誤報＝冤枉用戶），
所以規則應往漏報偏：**同部位＋同類型預設視為既有**，
除非尺寸或嚴重度明顯增加。紀錄條目需附 `reference_crop` 供視覺輔助比對。

**③ 初始紀錄從哪來。**
車輛入隊時需做一次基準拍攝並建檔，否則第一位租用者會承擔所有既有損傷的嫌疑。

### 若要驗證，該怎麼做

本次的 120 組人工標註配對可以改造成驗證資料：
把「借」側的標註結果當成合成紀錄，餵給 L1，看它能否正確找出「還」側多出來的損傷。

但要注意這只驗證了**機制**，沒有驗證**真實紀錄的品質**——
實務上紀錄會有漏登、描述不一致、久未更新等問題，那些是合成資料模擬不出來的。
因此完整驗證仍需 iRent 提供真實紀錄。
