# iRent Pulse — 車況分層檢測 API

`docs/return-car-docs/分層規格書_v1.md` 的 **L1／L2／L3** 伺服器端實作。
L0 在手機上（`lib/l0/`），這裡不碰。

| 層 | 這一層回答什麼 | 技術 | 時機 |
|---|---|---|---|
| **L1 快篩** | 這張照片能判讀嗎？看得到車損嗎？車內乾淨嗎？ | `google/gemini-3.7-flash` | **阻塞，使用者在等** |
| **L2 影像確認** | 這個損傷是這趟造成的嗎？ | `anthropic/claude-opus-5` | 非同步，使用者已離開 |
| **L3 決策派工** | 車輛該進什麼狀態？誰要行動？ | 規則引擎，**不是 AI** | 非同步 |

模型走 OpenRouter，金鑰讀專案根目錄的 `.env`：

```
OPENROUTER_API_KEY=sk-or-...
```

換模型不用改程式，加環境變數就好：`L1_MODEL` / `L2_MODEL`。

---

## 跑起來

```bash
api/run.sh
```

第一次會自己建 `.venv` 並裝套件。預設綁 `127.0.0.1:8000`，
給模擬器與 `flutter run -d chrome` 用。實機要連同一個 Wi-Fi：

```bash
api/run.sh 0.0.0.0
```

再讓 App 指過來（`InspectionApi` 預設在 Android 模擬器用 `10.0.2.2`）：

```bash
flutter run --dart-define=API_BASE_URL=http://192.168.x.x:8000
```

互動式文件在 <http://127.0.0.1:8000/docs>。

## 端點

| 方法 | 路徑 | 用途 |
|---|---|---|
| `GET` | `/healthz` | App 開拍前探測；探不到就退回腳本情境 |
| `POST` | `/v1/l1/screen` | 一張照片的阻塞快篩（multipart） |
| `POST` | `/v1/returns/finalize` | 對升級的照片跑 L2，再跑 L3 |
| `POST` | `/v1/l3/decide` | 純規則引擎，不呼叫模型，可離線重放 |
| `GET` | `/v1/orders/{id}` | 客服複核要看的東西：兩側照片、判定、`reason`、當時的留言板 |
| `GET` | `/v1/photos/{id}` | 取車／還車照片並排對照 |
| `POST` | `/v1/cars/{car_no}/notes` | 寫一則車輛歷程留言 |
| `GET` | `/v1/cars/{car_no}/notes` | 讀留言板；`?before=` 是 L2 套用的時間切點 |

`/v1/l1/screen` 的 `slot` 是 `左前／右前／左後／右後／後座`。
`後座`（以及 `車內`、`前座`…）會走車內整潔度的 prompt，其餘走車外車損的 prompt。

一次冒煙測試：

```bash
api/.venv/bin/python api/scripts/smoke.py exterior 左前 assets/images/return/camera_scene.png
api/.venv/bin/python api/scripts/smoke.py interior 後座 assets/images/return/shot_interior.jpg
api/.venv/bin/python api/scripts/smoke.py pair 左前 還車.jpg 取車.jpg
```

留言板走完整條路，不需要任何取車照——同一張照片跑兩次，一次帶 `--note` 一次不帶，
同一個凹洞會從「無法判定（停用・送客服）」變成「既有（放行）」：

```bash
api/.venv/bin/python api/scripts/demo_trip.py \
  --note "上一位使用者：後保險桿右側有一個洞，還車時已回報" \
  --return 右後=還車_右後.jpg
```

## 每一層的實作重點

### L1 — 為什麼可判讀性要先問

benchmark 實測：把可判讀性當成車損 prompt 的附帶問題問，
`retake_required` 在 200 次呼叫中觸發 **0 次**——包含一張暗到、糊到看不出東西的照片。
VLM 有強烈的「有問必答」傾向。

所以 `prompts.py` 裡的順序是硬性的：**先問能不能判讀，再問有沒有車損**，
並且明講「不可判讀時 `observed_damages` 必須是空陣列」。
`l1.py` 再做一次 early return——不可判讀就把車損結果丟掉，不寫入紀錄。

**可判讀性與覆蓋範圍是分開的兩個欄位。** 一張只拍到左前保險桿的特寫，
若那塊保險桿清清楚楚，就是「可判讀 ＋ 覆蓋不足」，它看到的裂痕照常記錄。
索賠案件的損傷照大多是特寫，把「距離過近」歸入不可判讀等於把最重要的樣本全部作廢。

調校方向是**高 recall**：L1 漏掉的永遠不會再被看到，誤報只是多花一次 L2。
所以 `escalate_to_l2` 的門檻是「看到任何損傷」，不是「看到嚴重損傷」。

重拍上限 3 次（`l1.MAX_RETAKES`）。超過就接受照片、標 `quality_forced`，
由 L3 轉「停用（`unassessable`）」。**沒有這個出口，使用者會被困在還車流程裡**，
那比漏判車損嚴重得多。

### L2 — 為什麼不要叫模型「比較兩張照片」

光線、角度、背景、地面全都不同，模型會把無關差異講成車損。所以拆成兩段：

```
Stage A（VLM）  分別描述兩張照片，以「車輛部位」為索引，互相不知道對方存在
Stage B（程式） 集合差：damages(還) - damages(取)
```

用**車輛部位**當座標系而不是像素座標：兩張照片對不齊，但「左前葉子板」
在兩張裡是同一個東西。

`verdict` 一定是三態。第三態是這一層最重要的設計：

| 值 | 條件 |
|---|---|
| `新增` | 還車照有、取車照沒有，**且該部位在取車照中清晰可見** |
| `既有` | 取車照就有 |
| `無法判定` | 該部位在取車照被遮擋／模糊／未入鏡 |

沒有 `無法判定`，取車照沒拍好的案例會被誤報成新傷而誤扣押金。

**第二個證據來源：車輛歷程留言板。** 上面那張表只有照片。真正花錢的情境是取車照
根本不存在或沒拍到那個角度——而那個凹洞上一位使用者早就打進留言板了。那句話就是
缺的證據。`app/board.py` 因此把留言當成**證詞**，判定順序固定為：

1. 同角度的取車照（證據）
2. **本趟開始前**寫的留言（證詞）
3. `無法判定`（交給人看）

**留言只能把判定往 `既有` 推**，永遠不能製造 `新增`——「有人這樣說」不是任何人
該被求償的標準。取車照拍到該面板乾淨時照片贏；只有 `confirmed` 的留言能構成矛盾，
而矛盾送人工，不上帳單。用到留言的 finding 會帶著 `note_id`，L3 再把留言原文
一起寫進車況履歷，客服打開爭議時看到的是句子本身，不是一個外鍵。

留言是自由文字，`board.parse` 用封閉字彙的字面比對加一小張同義詞表把它對回
`(部位, 類型)`。刻意做得笨，而且笨在安全的方向：解析不出來的留言等於沒寫過。

幻覺抑制：`temperature=0`、強制 JSON schema、中性問法、
prompt 明確排除水漬／反光／陰影／地面倒影，
以及 `severity ≥ 3` 的案例跑 3 次取多數（`SELF_CONSISTENCY_RUNS`）。

### L3 — 為什麼必須是規則不是 AI

可稽核（客訴時要說得出為什麼）、可調整（營運改門檻不用重訓）、
法遵（涉及金錢的決策鏈必須可解釋）。

核心原則兩條：

1. **狀態自動，行動經人。** AI 可以讓車「不可租」——保護性、可逆、保護下一位用戶。
   AI 不可以派人、不可以花錢、不可以扣款。
2. **AI 只能把車移出「可租用」。** 唯一自動放行的情境是規則 8（全數通過）。

規則表在 `l3.py`，順序即優先序，`tests/test_l3.py` 逐條釘住。兩個容易被改壞的地方：

* **規則 1（髒汙）排最前面是刻意的。** 髒汙 30 分鐘後就砸到下一位用戶臉上，
  車損金額大但理賠可以慢慢談。派工優先序是 髒汙 > 車損，與直覺相反。
* **規則 4（輕微新損 → 可租用）不是終止規則。** 它的狀態跟規則 8 一樣，
  讓它短路後面的保守規則只會換來風險。程式裡把它排到最後才評估。

## 測試

```bash
api/.venv/bin/python -m pytest api/tests -q
```

目前只涵蓋 L3，因為 L3 是唯一「同一組輸入必定得到同一個答案」的一層，
也是唯一直接決定車輛能不能租、要不要跟使用者收錢的一層。

L1／L2 的品質要用資料集量，不是用單元測試量。規格書 §L1／§L2 定義了要報哪些數字
（分類別的 precision／recall、trivial baseline、95% CI、干擾物子群），
資料集不在這個 repo 裡。

## 成本

實測（本機一次呼叫，含影像 token）：

| 呼叫 | 模型 | 延遲 | 成本 |
|---|---|---|---|
| L1 車外 | gemini-3.7-flash | 約 7–11s | ~$0.004 |
| L1 車內 | gemini-3.7-flash | 約 4–5s | ~$0.002 |
| L2 一組配對 | claude-opus-5 | 約 15s | ~$0.055 |

L2 比規格書估的 ~$0.03 貴，因為它跑的是 Opus。
規格書 §L2 說明了為什麼這裡不能省成 Gemini：
**只有 Opus 的信心分數答對與答錯分得開（0.89 vs 0.64），可以拿來路由**；
Gemini 是 0.97 vs 0.92，分不開。要省成本就得改用 severity 分流，
把 `L2_MODEL` 換掉之前先確認這件事。

照片在送出前會縮到長邊 1024px、JPEG q85（`config.MAX_IMAGE_EDGE`）。
影像 token 是成本的主要來源，這一步比換模型省得多。

## 儲存

`store.py` 是行程內記憶體 + `data/photos/` 的檔案。正式環境換成 Postgres + 物件儲存，
查詢形狀不用改：L2 要的是「這趟、這台車、這個角度的取車照」，
客服要的是「同一組照片並排 + 判定 + `reason`」。

**照片不會進版控**（`api/.gitignore` 排除 `data/photos/`）。
